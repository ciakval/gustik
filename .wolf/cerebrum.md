- **[2026-08-14] Dashboard UI text and compass labels are Czech, not English.** Mlok's explicit call when asked: the audience is Czech scout organizers and the rest of the UI was already Czech, so the compass uses `S/SV/V/JV/J/JZ/Z/SZ` (`backend/src/static/compass.js`). - **[2026-08-14] For aggregated wind speed, show average AND the min-max gust band, not just an average.** Mlok's call: gusts are the actual safety signal for this project (P550 capsize risk), and a plain average over a 30s+ bucket averages away exactly the peak that matters.
- **[2026-08-14] Diagnostics/debug pages get a small footer link, not a hidden URL.** The backend is public and unauthenticated by design (FR-9), so hiding `/status.html` buys nothing and costs reachability from a phone on the boat.
- **[2026-08-15] For hardware bring-up and calibration, Mlok wants DUMB firmware and SMART host-side analysis. Standing preference, stated as a correction; it overrides the instinct to build a self-interpreting on-device diagnostic.** The firmware's job is to sample the peripheral and print raw numbers, nothing else. Capture the serial stream to a file, then do ALL interpretation on the host in throwaway Python. Do not put datasheet tables, cluster detection, failure-mode naming, or "VERDICT:" lines on the microcontroller. The whole sketch is ~20 lines:
  ```cpp
  #include <Arduino.h>
  static const uint8_t kPin = 34;
  void setup() { Serial.begin(115200); analogReadResolution(12);
                 analogSetPinAttenuation(kPin, ADC_11db); pinMode(kPin, INPUT); }
  void loop()  { Serial.printf("READING: mV=%u adc=%u\n",
                   analogReadMilliVolts(kPin), analogRead(kPin)); delay(50); }
  ```
  Give it its own PlatformIO env (`build_src_filter = -<*> +<the_file.cpp>`) so its `setup()`/`loop()` never link alongside `main.cpp` — that duplicate-symbol constraint is real and applies to any bring-up sketch. **Delete the sketch and the capture once the constants are extracted**; both are scaffolding, and Mlok asked for them gone rather than maintained. The lasting artifacts are the measured table in the source, the tests pinning it, and the method write-up in `docs/hardware/wind-sensor-wiring.md`.
  - **Why this is better, concretely, from the run that proved it:** raw data can be re-questioned with a hypothesis you did not have when you captured it. The same 18337-sample capture that confirmed the 8-octant calibration ALSO yielded the 16-position half-detent mis-decode (bug-050) on a second pass, from a question nobody had asked yet — no reflash, no second capture, seconds of compute. An on-device verdict cannot be re-questioned without rebuilding and re-flashing, and by then the hardware has moved.
  - Host-side analysis is also testable, diffable, disposable, and costs no flash. On-device interpretation is untestable C++ on the critical path of a measurement (see Do-Not-Repeat).
  - Two ESP32 specifics worth keeping: `analogReadMilliVolts()` is eFuse-calibrated and `analogRead()` is not, so print both but know they are **two separate conversions** — the two numbers on one line are not the same sample. And the ADC is severely compressed at the bottom of its range (a divider predicting 392 counts read 209), so cluster low-end levels with a tighter gap threshold than you would use up top.

## Key Learnings

- **Project:** gustik
- **[2026-08-16] Status LED panel settled at NINE LEDs in two groups — `R Y G B ⎢ G G Y Y R` — after two earlier layouts were rejected for the same reason.** Full spec: `docs/superpowers/specs/2026-08-16-status-led-panel-design.md`. The rejected layouts were 4 LEDs re-purposed per mode, and 8 as two identical `R Y G B` quads. **Both failed because colour carried two incompatible meanings at once**: in the status lanes colour is *identity* (yellow = radio), in a bar it is *magnitude* (yellow = middling), so the reader had to know the mode before a colour meant anything. Fix: make the two groups different *kinds* of display — a mixed-colour cluster reads as separate indicators, an ordered green→red ramp reads as a meter, and both idioms are already universal. Left group (4, on 32/33/25/26) never changes, so going to look at wind or signal can never hide a fault. Right group (5, on 19/18/17/16/4 — **GPIO5 sits physically between 18 and 17 and is skipped**) shows **exactly one lit dot**, sliding left→right as things worsen. Three reasons it is a dot and not a filled bar, all learned the hard way: a fill invokes the phone "more bars = better" convention and that fights wind (where more = worse); the original spec filled *from the red end*, so red was lit at every level ≥1, fighting the fault lane; and a dot is read by colour alone, no counting. Free bonus: position redundancy keeps it readable with red-green colour deficiency. Power barely moves (dot = 1 LED): ~15 mA worst case vs ~13 mA for four.
- **[2026-08-16] Battery sense measures the 5 V RAIL, not the pack, and deliberately does NOT try to detect USB — it will false-alarm on a USB-powered bench board, and that is the accepted design.** USB reads ~4.6-5.0 V on `V5`, *inside* the low-battery warn band (4.6-5.0 V), so a nearly-flat pack and a USB rail are genuinely indistinguishable by level; there is no way to attach probes to the pack itself, so a pack-side tap is unavailable. A USB-detecting "arm latch" was specified and then **removed by Mlok's decision to simplify**. The reasoning to preserve: any side-channel battery-detection scheme adds a second invisible state that can itself be wrong (a pack booting already part-used would never arm, silencing the alarm exactly when needed), and **a loud panel on the bench is a cheaper failure than a quiet one on the water** — USB is not present in the deployed configuration at all. Escape hatches that need no new mechanism: omit `-DGUSTIK_PANEL_BATTERY=1` in bench builds (intended workflow), long-press hard-off, or `leds.enabled=false`. **Never** widen the `unknown` band to swallow the USB range — that swallows a genuinely flat pack too. Related ADC facts worth not rediscovering: **ADC1 at 11 dB is only usable to ~2450 mV**, so a 1/3 divider cannot represent more than ~7.35 V — the "implausibly high ⇒ divider miswired" check must test for *a full-scale-pinned raw reading*, not for a voltage above 8 V, which is unreachable. And **there is no capacitor on hand**, so the usual 100 nF from tap to GND is out: with three 10 kΩ resistors, wire them as **10 kΩ top / 2 × 10 kΩ in parallel (5 kΩ) bottom** rather than 20 kΩ top / 10 kΩ bottom. Same ratio 1/3 from the same three parts, but source impedance 3.3 kΩ instead of 6.7 kΩ — which is most of what the cap would have bought — for an extra 214 µA (2.1 mAh/day, irrelevant). Filtering then falls entirely to the firmware EMA + 3-cycle confirmation.
- **[2026-08-16] Flash layout facts — the device has ONE 4 MB flash chip, not two, and `config.txt` IS on LittleFS (a belief that it was written "raw to data flash" was wrong).** Full writeup in `docs/hardware/flash-memory-map.md`. The partition table moved from Arduino's `default.csv` to `firmware/partitions_gustik.csv` (dropped the never-used second OTA app slot): **flash 92.4 % → 57.7 %**, app partition 1.25 → 2 MB, LittleFS 1.375 → 1.875 MB, same source, verified by build. Three traps worth not rediscovering: (1) **the data partition must keep the name `spiffs` even though it holds a LittleFS image** — `LittleFS.begin()` defaults to `partitionLabel="spiffs"` (`framework-arduinoespressif32/libraries/LittleFS/src/LittleFS.h:27`), so renaming it to `littlefs` makes `config.txt` and the offline buffer silently unreadable, same failure class as bug-028; (2) `app0` keeps subtype **`ota_0`, not `factory`**, because the Arduino toolchain flashes `boot_app0.bin` into `otadata` on every upload and expects to boot `ota_0` — one slot is what kills OTA, not the subtype; (3) a table change **moves the filesystem**, and `LittleFS.begin(formatOnFail=true)` silently formats the new empty partition, so a reflash must ALWAYS be followed by `pio run -t uploadfs` or the device boots with no WiFi/token and says nothing useful. Also: the Arduino core in use is package `3.20011.230801` = **Arduino-ESP32 2.0.11**, not "3.x" as `platformio.ini`'s header comment claims — PlatformIO's package version is not the core version.
- **[2026-08-16] The dev board is a 38-pin "ESP32 DevKit v1 / NodeMCU-32S"-style board, NOT the 30-pin DevKitC that the LED-panel spec's first draft assumed — probed over serial, don't re-guess.** `esptool.py flash_id` on `/dev/ttyUSB0` reports **ESP32-D0WD-V3 rev 3.1** (the die in a WROOM-32E module), **4 MB flash, manufacturer 0x5e (Zbit)**, 40 MHz crystal, bridge **CP2102** (`10c4:ea60`), MAC `30:76:f5:b9:13:04`. Probe command (the packaged `esptool` shim is not executable; call the `.py` directly): `cd ~/.platformio/packages/tool-esptoolpy && ~/.platformio/penv/bin/python esptool.py --port /dev/ttyUSB0 --no-stub flash_id`. Three things this settles: (1) **`VRef calibration in eFuse` is present**, so `analogReadMilliVolts()` has a real calibrated reference (~±3 %) — the battery-sense design in the LED spec §4.7 is sound on this chip; (2) **4 MB flash confirms** the 1 310 720 B app partition figure and the `partitions_gustik.csv` 92.4 %→57.7 % math; (3) **GPIO6–11 are physically broken out** on this board as `CLK/SD0/SD1/SD2/SD3/CMD` at the bottom of both columns — they are the SPI flash bus, they look free and are not, and **`V5` sits immediately adjacent to `CMD`/GPIO11**, which is exactly where the battery pack `+` lands. Pin layout, left column top→bottom: `3V3 EN 36 39 34 35 32 33 25 26 27 14 12 GND 13 SD2 SD3 CMD V5`; right column top→bottom: `GND 23 22 TX 21 GND 19 18 5 17 16 4 0 2 15 SD1 SD0 CLK` (with RX between TX and 21). Happy consequence: the whole planned panel (vane 34, battery 35, LEDs 32/33/25/26, anemometer 27, GND, button 13) is **one contiguous 11-pin run down the left column with a GND in the middle of it**. Silkscreen calls the 5 V/VIN pin **`V5`**. Unknown and only answerable with a multimeter: whether this (likely clone) board fits the USB-VBUS→V5 protection diode — measure `V5`→GND on USB with the pack disconnected; ~4.6–4.85 V means a Schottky is present, ~5.0 V means direct and pack+USB must never be connected together.
- **[2026-08-16] The Station's supply is 4x AA (~3000 mAh), NOT a powerbank — every power estimate written before this date assumed a 10 000 mAh powerbank and is wrong by 3.3x.** The powerbank auto-shut-down after ~2 h even in "low output" mode (bug-061); a race day needs 8-10 h. Consequences worth remembering rather than re-deriving: runtime is `usable mAh / average mA` regardless of pack voltage, so at ~120 mA the pack is the binding constraint, not the regulator; **alkaline, not NiMH** (4x NiMH is 4.8 V nominal and sags into the DevKitC AMS1117's dropout with most of the charge unused, whereas 4x alkaline starts ~6.4 V); the linear regulator burns ~45% of a 6 V pack as heat, so a **~2 EUR buck converter would roughly double runtime on the same cells** - a far bigger win than anything else on the table; and 3000 mAh is a low-current rating that will under-deliver at 120 mA. **Also: there is no enclosure and v1 will deploy in a cardboard box**, so nothing needs drilling, sealing or light-piping yet, and an operator can simply look inside - which retires the "will LEDs be visible in sunlight" worry for v1 and defers the reed-switch button idea to Story 5.2.
- **[2026-08-16] Indicator-LED hardware facts for this build, confirmed by Mlok — settle for these, don't re-derive.** The kit's red/yellow/green/blue LEDs are all **Vf 2.0–2.4 V** parts (blue measured 2.6 V), and **330 Ω is the only resistor value available** — all four light visibly on it, ~2.1–3.9 mA each, ~13 mA with all four on. So: **one resistor value on every lane**, no per-colour sizing, and the usual bright-green-InGaN trap (Vf 2.9–3.3 V, barely lights from a 3.3 V rail) **does not apply to this kit**. Still unverified and the only open hardware question: whether 2–4 mA is visible in **direct sunlight** — shade the panel rather than raising current if it is marginal (220 Ω → 4–6 mA is the fallback). Separately: **the three LEDs that have been in the firmware since Story 2.4 / the 2026-08-11 bring-up (GPIO2 disconnect, 25 config-loaded, 26 WiFi-connected) were never physically fitted and have never been read by anyone.** Those pins are free to reassign with no migration concern — and it means FR-5's "signal a lost connection" has never actually been satisfied in the field, only in code.
- **[2026-08-15] Reading the ESP32's serial stream from Python needs no pyserial, and shouldn't use it.** `pyserial` isn't installed for this machine's system python and `uv` isn't on PATH here either, so anything that must "just run" has to be stdlib-only. `os.open(port, O_RDONLY|O_NOCTTY|O_NONBLOCK)` + explicit `termios` flags + `select` is the whole dependency list (`scripts/src/gustik_scripts/esp32_serial.py`) — and it *attaches without resetting the board*, where pyserial toggles DTR/RTS and reboots the ESP32 mid-capture. `O_NONBLOCK` matters at open() time too: without it, opening a tty blocks until carrier is detected. Measured 48 Hz from a `delay(20)` sketch, matching ground truth from `stty` + `cat`. Two real-stream properties worth designing for, both observed: the first line is usually a **fragment** (you attach mid-line), and the sketch's own `#` diagnostics are interleaved — so parse defensively and skip anything unparsable rather than raising.
- **[2026-08-15] Calibrate the magnetometer through the ESP32, not through the USB-I2C bridge.** A calibration describes one rigid assembly, so the bench rig (`--bus 18`, MCP2221, smbus2) calibrates the *wrong thing* — the numbers that ship must come from the station's own board, breadboard, base and wiring. `scripts/src/gustik_scripts/mag_calibrate.py` is that front end; it reuses `calibration.py`/`orientation.py` unchanged and shares the verdict text with the bench tool via `report.py` (one copy, deliberately — two would eventually disagree about what "good enough" means). `gustik_scripts/__init__.py` imports `QMC5883P` lazily via PEP 562 `__getattr__` so the stdlib-only serial path stays importable on a machine that has never installed smbus2.
- **[2026-08-15] The magnetometer Y sign flip has exactly one correct home, and it is the host script's output.** `sense/magnetometer.cpp` negates Y as it reads (mount up=-z/forward=+x), so the offset `correct/wind_direction.cpp` subtracts must be negated relative to the raw JSON. `firmware_output.firmware_hard_iron()` applies it once, so both emitted forms (config.txt lines and the C++ constant) are paste-ready and the firmware applies them verbatim. The JSON keeps the chip's own frame because `orientation.py` reasons in it. Getting this backwards mirrors the heading about north-south and reports no error — `tests/test_firmware_output.py` pins it from both directions.
- **[2026-08-15] Magnetometer hard-iron offsets are now readable from `config.txt` (`mag.offsetX`/`mag.offsetY`), not only compiled into `main.cpp`.** Both keys or neither — a half-applied hard-iron correction rotates the heading by an arbitrary amount, which is worse than no correction — and a non-numeric value is treated as absent rather than parsed leniently. `main.cpp` prints which set is in force at boot (`from config.txt` vs `compiled-in default`), because a wrong offset otherwise produces a confident, stable, wrong heading with nothing reporting an error. Rationale for the config route: recalibrating after a remount costs `pio run -t uploadfs` instead of a rebuild + reflash, and the sensor is expected to move again before the final enclosure.
- **[2026-08-15] Bring-up sketches need their own PlatformIO env, and should be deleted once they have done their job.** Each has its own `setup()`/`loop()`, so linking one alongside `main.cpp` is a duplicate-symbol error: give it `build_src_filter = -<*> +<the_file.cpp>` and, if the sketches live in a subdirectory, exclude that directory from `[env:esp32dev]`. A bring-up sketch should depend on *nothing* else in `src/` — no WiFi, no config.txt, no other sensors — so a failure it reports is unambiguously about the one peripheral under test. **They are scaffolding, not deliverables:** `firmware/src/diag/` and its two envs were deleted 2026-08-15 once the vane constants were extracted, along with the CI job that had been build-verifying them. Do not carry a bring-up sketch (or its captured data) in the tree "in case it's useful" — re-writing 20 lines costs less than maintaining and CI-guarding them, and the knowledge belongs in `docs/hardware/` plus the tests. **Amended 2026-08-16:** Mlok asked for `src/diag/pulse_diag.cpp` (anemometer) to be *committed*, so the rule is not absolute — the "delete it" step is a judgement call made when the sketch has served its purpose, not something to do unasked. - **[2026-08-15] The wind vane is confirmed good on real hardware, and the placeholder calibration it was going to run against was actively wrong.** Measured on the real ESP32 + real vane: all 8 octants read as distinct, stable levels (ADC spread 0-4 counts, ≥99 mV between adjacent octants) matching Fine Offset's ladder with a uniform +4-6% systematic offset. Measured `{2944, 1664, 210, 573, 974, 2315, 3855, 3466}` vs the placeholder `{3200, 1600, 2200, 3800, 3950, 3450, 2800, 2400}` - only 45° was close, 90° was off by ~2000 counts (see bug-045). Treat "placeholder constant" in a nearest-match lookup as a correctness bug in waiting, not a tuning task. **Follow-up the same day: measuring the 8 octants was still not enough** — the vane rests at 16 positions, and three of the unlisted ones decoded up to 112.5deg wrong (bug-050, now fixed with a 16-entry table in `sense/vane_decode.cpp`). Measured values + method: `docs/hardware/wind-sensor-wiring.md`.
- **[2026-08-15] Capturing serial from this machine: the board is at `/dev/ttyUSB0` and `pyserial` is NOT installed for the system python3, so the DTR/RTS reset trick is unavailable - `stty -F /dev/ttyUSB0 115200 raw -echo` + `timeout Ns cat` attaches without resetting, which means the boot banner is usually already gone.** Design bring-up sketches so nothing important lives only in the boot banner; put the constants and the verdict in the *periodic* output instead. - **[2026-08-16] The vane and the magnetometer are one instrument, and their mutual alignment is an unwritten precondition of `correctWindDirectionOctant()`.** `absolute = vane + yaw (mod 8)` is only valid because both terms are measured clockwise from *the same reference axis*: the vane's 0° mark (electrically the 33 kΩ reed, ADC ~2943) and the magnetometer's `forward` axis must point the same way — conventionally the bow. The magnetometer's mount is *not* free either: `sense/magnetometer.cpp` hard-codes `up = -z, forward = +x` (board component-side DOWN, +X to the bow, +Y falling to starboard), and mounting it the other way up mirrors the heading so the error grows with heading instead of being constant — which a single-heading spot check passes. There is **no mount-offset constant** anywhere; alignment is a physical requirement. On this boat the head's arms are athwartships (vane starboard, anemometer port), so sensor E → starboard and sensor N → bow. The anemometer's own direction is irrelevant (omnidirectional cups). Documented with failure signatures and a 3-step acceptance test in `docs/hardware/sensor-orientation.md`; the WH1080's shore instruction ("point one arm west") is deliberately broken on a boat — the head aligns to the hull and the magnetometer supplies the world reference. Also: calibrate hard-iron **in place by swinging the boat level**, not with `--tumble` — the firmware reads only X/Y, so a level 360° turn captures exactly what is used and folds in the boat's own signature.

POST /readings now rejects non-canonical `capturedAt` with 400 (see ingest/routes.js `ISO_8601_UTC` regex). If you ever touch capturedAt handling again: real firmware always emits exactly `%Y-%m-%dT%H:%M:%S.000Z` (firmware/src/transmit/hw/clock.cpp) — validate against that exact shape, don't loosen it to "anything Date.parse accepts" or this class of bug returns.

- **[2026-08-16] The LED panel is IMPLEMENTED (spec phases 1+2) and `firmware/src/indicate/` is now a third pure-logic directory in the native test build.** `pio test -e native` 57 -> **137 tests**; `esp32dev` flash 57.7% -> **58.0%** (+5 048 B), RAM +288 B. Structure mirrors `sense/`/`correct/`/`transmit/`: pure modules (`pattern`, `fault`, `panel`, `button`, `panel_inputs.h`) at the top level, hardware under `indicate/hw/` (`led_panel`, `button_pin`, `panel_pins.h`), and `platformio.ini`'s `[env:native]` filter gained `+<indicate/*.cpp>`. Four design points that paid off and are worth reusing:
  1. **One `LanePattern` struct instead of an enum of named patterns.** `{flashes, onMs, offMs, pauseMs, oneShot, inverted}` expresses solid, 1 Hz, 4 Hz, a 60 ms heartbeat pulse, a double pulse, an N-flash fault code, a one-shot mode banner and an inverted "dark notch" lane - all of them - which makes the renderer nine `digitalWrite`s and puts every timing under test. `isLit(pattern, nowMs, phase0)` uses unsigned arithmetic throughout, so a millis() rollover costs one mistimed blink rather than a stuck lane (pinned by a test).
  2. **`Lane = pattern + phase0`.** A pattern without its anchor cannot be rendered: a fault code must start at flash 1 the moment the fault appears, not wherever a free-running clock happens to be. Continuous patterns anchor at 0, which has the free bonus that every slow-blinking lane blinks in unison.
  3. **The status/detail split is asserted, not hoped for.** `test_panel_modes` compares the whole status group byte-for-byte across all three detail modes; `detailPositionsInUse()` asserts the one-dot rule in wind and signal mode, since the renderer deliberately does not enforce it.
  4. **Gestures decide on RELEASE.** A long press passes through short-press duration on its way, so deciding on press would make hard-off also cycle the mode.
- **[2026-08-16] "Absent hardware is a no-op" and "one-way data flow" are the two invariants that make an optional firmware feature actually optional - and both are cheap to test.** `PanelInputs` is a plain struct copied once per cycle; nothing downstream of it may write to anything upstream (design constraint C3), which is why `connectedNetworkIndex()` derives the network from `WiFi.SSID()` in `main.cpp` rather than plumbing a getter out of `WifiTransmitClient`, and why `Anemometer::pulseCountSnapshot()` is a separate non-resetting read beside `readAndResetPulseCount()` rather than a change to it. The button side needs no code at all: `INPUT_PULLUP` with nothing attached reads released forever, which `test_button` pins directly. **The one thing this does NOT buy is zero flash when compiled out**: `-DGUSTIK_STATUS_PANEL=0` measured **+1 032 B** over the pre-panel baseline, because three helpers live outside the flag on purpose (`vaneAdcPlausible()`, `pulseCountSnapshot()`, the `leds.*` config keys). Guarding the config parser would make a `config.txt` behave differently depending on how the firmware was built - a worse trade than a kilobyte out of 881 KB free.
- **[2026-08-16] A total lookup function cannot report broken wiring, so the plausibility check has to be a separate, differently-shaped question.** `vaneOctantForAdc()` is total by design (nearest-match over 16 anchors), so an open GPIO34 pulled to 4095 decodes to a confident, stable 270deg. The panel needed "is the vane even connected", which is `vaneAdcPlausible()` - and it is a **RANGE check (60..4000), not a "within N counts of the nearest anchor" check**, because a turning vane genuinely passes through intermediate resistances and an anchor-proximity test would cry wolf on a working sensor in a gusty wind. The failure modes worth signalling (open, short) both leave the band entirely. Generalise: when adding a health check beside a total decoder, ask what the *failure* looks like in the raw signal, not how far it is from the nominal states.

- **[2026-08-15] A coverage metric computed on *normalised* data cannot detect the absence of motion — and will confidently report full coverage for a sensor that never moved.** `calibration.describe_spin()` rescales each axis by its own span before assigning samples to sectors, so a motionless magnetometer's noise (symmetric, ~40 LSB) scatters across all 12 sectors and reports `12/12 sectors covered, all three axes swept` — a perfect score for a capture where nobody turned the board (bug-058). The derived hard-iron offsets are then just wherever the sensor happened to point, which is exactly the "stable, confident, wrong, no error anywhere" failure as the vane's bad anchor table (bug-045). **Whenever a quality metric normalises away scale, something else must check the scale.** Fix here: `firmware_output.motion_warning()` judges the raw peak-to-peak span (~40 LSB stationary vs ~1500 LSB for a real Czech level turn) against a range-scaled 0.08 G floor, is printed *before* the coverage verdict because it invalidates it, and makes the CLI exit non-zero. Generalise: before trusting any "N/N covered" figure, ask what it divided by.
- **[2026-08-15] `cfmakeraw()` lives in `tty`, not `termios`, and only from Python 3.12** — despite every other `cf*`/`tc*` helper being in `termios` (bug-057). For a tool meant to run under whatever `python3` is on the machine, don't use it at all: set the raw-mode flags explicitly (clear `IGNBRK|BRKINT|PARMRK|ISTRIP|INLCR|IGNCR|ICRNL|IXON`, clear `OPOST`, clear `ECHO|ECHONL|ICANON|ISIG|IEXTEN`, clear `CSIZE|PARENB`, set `CS8`), which is ~10 lines and has no version floor. - **[2026-08-14] Never plot a circular quantity (wind direction) on a linear axis, and never take an arithmetic mean of one.** Both mistakes shipped in Story 3.2 and survived until Mlok looked at real data (bug-037). - **[2026-08-16] On-boat observability = a 4-LED panel + 1 button, layered, and optional in three independent ways. Route A (`std` on ESP-IDF via `esp-idf-svc` 0.52.1) is lower-risk and would be the pick if shipping mattered - it was rejected *only* because it teaches ESP-IDF-in-Rust rather than embedded Rust. Two decisions worth remembering: (1) **the ESP32-WROOM is Xtensa, so `espup`'s compiler fork is still mandatory as of Aug 2026** - the `xtensa-esp32-*` targets are Tier 3 *specs* upstream but stock rustc's LLVM has no Xtensa backend enabled; every bit of that friction vanishes on a RISC-V C3/C6, which is a real open question for a learning project. (2) **TLS is the one genuine ecosystem gap**: the backend is HTTPS and the firmware carries a bearer token, but `embedded-tls` (the crates.io option) does not verify certificates in `no_std`; `esp-mbedtls` does but is git-only, and `reqwless` must also be a git dep to use it. Plan keeps all pure logic in a route-agnostic `gustik-core` crate precisely so a late pivot to Route A rewrites only `main.rs`. Full study: `docs/rust-firmware/` (5 docs + README), with 8 open questions in `05-open-questions.md`.
- **[2026-08-14] Mlok answered Q1-Q4 of the Rust study the same day; all six docs re-spun to match.** (1) **Chip stays ESP32-WROOM/Xtensa** - RISC-V acknowledged as the friction-free option but he has none at hand. (2) **`no_std` confirmed.** (3) **TLS: certificate verification explicitly NOT required** - *"security is not really important here... encryption is still good, because it prevents the API from being trivially exploitable (no sniff of the bearer token). I don't assume malicious actor with an AP here."* This is an informed, deliberate risk acceptance, recorded as such in `03-risks-and-gaps.md` - **do not re-litigate it in future sessions.** It collapsed the study's biggest risk: `reqwless` + `embedded-tls` are both on crates.io, so no git deps on `esp-mbedtls` and no mbedTLS in the flash budget. (4) **Use the `qmc5883p` crate** rather than hand-writing a driver, reasoning that upstreaming fixes beats a private implementation - so the planned `gustik-drivers` crate was dropped from the workspace layout.
- **[2026-08-14] Two load-bearing claims in the Rust study were verified against reality rather than assumed - both reusable facts.** (a) `curl --tls13-ciphers TLS_AES_128_GCM_SHA256 --curves X25519 https://gustik.remesh.cz/health` returns 200, proving the live Caddy backend completes a handshake restricted to exactly what `embedded-tls` implements. This was a genuine question, not a formality: the server's *default* negotiation with a modern client picks `X25519MLKEM768` + ChaCha20-Poly1305, **neither** of which embedded-tls offers - it only works because Caddy falls back cleanly. The cert is **ECDSA (`id-ecPublicKey`), not RSA**, which matters because `reqwless` calls out alloc/handshake cost specifically for RSA certs. (b) The `qmc5883p` crate's register map matches the map already proven on our board (`0x2C`, CTRL1 `0x0A`, CTRL2 `0x0B`, data at `0x01`, `0x29=0x06`) - **except it never writes `0x0D = 0x40`**, which both `sense/magnetometer.cpp` and `scripts/src/gustik_scripts/qmc5883p.py` do as part of QST's reference init sequence. Our own bench notes say the sensor works without it, so that's the first thing to try if crate readings look wrong, and the obvious first upstream PR. **Tooling note: `openssl s_client` produced no output at all in this environment while `curl` worked fine - use `curl -v` / `--tls13-ciphers` / `--curves` for TLS introspection here.**
- **[2026-08-14] Graph time control is Grafana-shaped: a range picker with auto-derived resolution, not a resolution picker.** Mlok asked for "the resolution of the graph, maybe 1 hour by default, somewhat Grafana-style". Implemented as range chips (15 min / 1 h / 3 h / 6 h / 12 h / dnes, default **1 h**) with the bucket width auto-derived to ~180 points and snapped to a shared "nice numbers" ladder (`BUCKET_LADDER_SECONDS`, duplicated in `serve/aggregate.js` and `static/timerange.js`, kept in sync by a test). The resolution stays overridable via a select, and the *effective* value is always displayed - including when the server coarsens it to stay under its 2000-point cap, which the client reads back off the response rather than assuming its request was honoured. Aggregation happens **server-side** (`GET /readings/history?from&to&bucket`) rather than in the browser: a race day is ~28 800 rows at the firmware's 3s cadence and shipping all of them to a phone on a boat hotspot to throw most away is the wrong end to solve it at. Empty buckets are omitted, never zero-filled - a gap must look like a gap, not like a calm.
- **[2026-08-14] The diagnostics page's ingest log is in-memory and deliberately not persisted.** `fastify.ingestEvents` is a 100-entry ring buffer written by `POST /readings` and read by `GET /readings/status`. It records `{count, inserted, duplicates, backfilled, remoteAddress}` per batch - the one thing the `readings` table structurally cannot reconstruct, because a batch whose rows all collide on `client_id` leaves *no trace at all* (`ON CONFLICT DO NOTHING`, and the route answers 201 regardless). That is exactly how bug-031 stayed hidden for hours. Chose the ring buffer over a new table: no schema change, no growth management, and "what is the device doing right now" genuinely does not need to survive a restart. Note this makes the duplicate case *visible* but does NOT change the `POST /readings` response contract - that remains the separate open follow-up flagged after bug-031, since it is firmware-facing.

- **[2026-08-10] Backend deploy moved to a GHCR registry-push flow, GHCR image kept private with a fresh ephemeral login every deploy.** Was: CI verifies the Dockerfile builds, then rebuilds it again from source on the server (`docker compose up -d --build`) - two separate builds of the same commit, no guarantee they produce identical bytes. Now: CI's `build-backend-image` job builds once and pushes to `ghcr.io/ciakval/gustik-backend` (`:latest` + `:<sha>`, only on pushes to `main`); `deploy-backend` ships only `compose.yaml` to the server (not the source tree) and does `docker compose pull && up -d` - the server runs the exact image CI already build-verified. Chose to keep the GHCR package **private** even though the repo itself is public: a fresh `docker login ghcr.io` on the server using that run's own short-lived `GITHUB_TOKEN` (piped via stdin, same discipline as the `.env`-from-secret write step - never a CLI arg) costs nothing extra per deploy and needs zero manual "make the package public" step in GitHub's UI to remember. `compose.yaml` keeps both `image:` (what's deployed) and `build: .` (so local dev / `docker compose up --build` still works unchanged).
- **[2026-08-10] `docker-compose.yml` renamed to `compose.yaml`.** Docker Compose v2's preferred/canonical filename (Mlok's call) - `docker compose` (the v2 CLI, no hyphen) auto-detects `compose.yaml` before falling back to the legacy `docker-compose.yml`, so no `-f` flag needed anywhere (local dev, CI, or the server). ## Key Learnings (session-process notes)

- **[2026-08-14] `.wolf/anatomy.md`'s auto-scanner overwrites hand-written file descriptions whenever the file's content changes** - it regenerates the description from the file's H1 heading, so a carefully-written one-line summary silently reverts to e.g. "03 - Risks and gaps" the next time you edit that file. OPENWOLF.md says hand edits "are absorbed on the next update", which is true only if the file itself hasn't changed. Practical rule: **write anatomy descriptions LAST, after the files are final**, or expect to redo them. Hit this twice in one session on `docs/rust-firmware/`.

- **[2026-08-01] `actionlint` (+ `shellcheck` for embedded run: scripts) catches real GitHub Actions mistakes that plain YAML parsing can't.** Not preinstalled; grab the binary via `curl -sL https://raw.githubusercontent.com/rhysd/actionlint/main/scripts/download-actionlint.bash | bash` (drops `./actionlint` in cwd) and `sudo apt-get install -y shellcheck` for the deeper check. Caught a real bug while writing `.github/workflows/ci.yml`: a job-level `if:` condition referencing `secrets.X` - the `secrets` context is not available in job-level `if:` at all (only `github`, `inputs`, `needs`, `vars` are), a mistake plain `yaml.safe_load()` can't catch since it's valid YAML/valid expression syntax, just semantically wrong for that context. Always run `actionlint` against new/changed workflow files before pushing - GitHub Actions failures are slow and annoying to iterate on compared to a local lint pass.
- **[2026-08-01] A "verified" architecture decision made before ever actually attempting the underlying build is not verified - go run it before trusting it, even under a plausible-sounding excuse ("hardware-gated") for why it wasn't tried.** The ESP32 Arduino core version pin (2.x, decided at architecture time) was accepted as final for the whole implementation phase on the assumption that building `[env:esp32dev]` needed physical hardware - it only needed internet access, which was available the entire time. Only surfaced as broken when the CI pipeline task actually ran `pio run -e esp32dev` for the first time (see buglog bug-017). Lesson: "this needs hardware to verify" is worth a second look before accepting it as a reason not to try - a devcontainer's tool availability isn't the same as a build's actual requirements.
- **[2026-08-01] Real headless-browser smoke testing is available and worth using for dashboard stories.** `puppeteer-core` ships bundled with the globally-installed `openwolf` npm package (`/usr/lib/node_modules/openwolf/node_modules/puppeteer-core`) but has no browser binary of its own. `sudo apt-get install chromium` (~90MB, fast) provides one at `/usr/bin/chromium`; launch with `puppeteer.launch({executablePath: '/usr/bin/chromium', headless: true, args: ['--no-sandbox']})` (sandbox needs to be disabled running as root/in this container). Used in Story 3.2 to actually render the dashboard, confirm the Chart.js canvas has real pixel content (not blank/crashed), and check for console/page errors - caught nothing that session but is real coverage server-side `node:test` assertions structurally cannot provide (any DOM/Chart.js/browser-JS runtime error). Worth repeating for Story 3.3 and any future dashboard changes.
- **[2026-08-01] For every backend story, run a real smoke test (actual `node src/index.js` + curl) in addition to the injected/`:memory:` test suite before merging.** Story 1.6 caught a real bug (buglog bug-011: `openDb()` never created the DB file's parent directory) that all 22 passing `node:test` assertions missed, purely because every test uses `dbPath=':memory:'` and never touches the filesystem or starts a real listener. In-memory injected tests are fast and good for logic, but they cannot catch filesystem/startup/real-network issues - a quick manual boot + curl round-trip is cheap insurance every backend story should do before calling itself done, not just when something feels risky.
- **BMAD skill workflows assume a live interactive user at every menu ("halt and wait for [C] Continue").** When one of these skills is run inside an autonomous subagent invocation (Agent tool, no attached interactive user), there is no way to literally pause across turns — the skill's step files must be read and followed for *content/structure* discipline (extraction rigor, dependency rules, coverage validation), but the halt-for-approval menus have to be resolved using whatever brief/context the invoking session provided, standing in for the user's answers. Always flag this explicitly in the output (both in the artifact itself and in STATUS.md) so the real user knows no live back-and-forth happened and should spot-check the result once.

- **[2026-08-16] LED panel phases 1+2 shipped on `feat/status-led-panel`; phase 6 (battery sense) deliberately NOT built, and two spec details were changed during implementation rather than followed literally.** Both changes are recorded in the spec itself, because a spec that quietly disagrees with the code is worse than either.
  - **Yellow's "fast blink = scanning / connecting" is not implemented.** This firmware connects synchronously inside `send()`, so there is no scanning state to report - not associated is simply *off*, per Q4. Inventing the state would have been a lie told in LEDs. The encoding is left in the design for whenever the connect path becomes non-blocking.
  - **The status yellow lane's slow-blink threshold is -75 dBm, and -67..-75 reads as solid.** The spec's table left that gap unspecified (solid at >= -67, blink at < -75). Chosen deliberately: a lane that blinks at a perfectly usable signal trains people to ignore it.
  - **Phase 6 is out of scope on purpose.** It needs a resistor divider that is not fitted, it is independently flagged (`-DGUSTIK_PANEL_BATTERY=1`), and the spec sequences it after phase 5 ("one regatta day of real use"). Building it now would mean shipping an alarm nobody can verify.
