## Key Learnings

- **Project:** gustik
- **[2026-08-01] `@fastify/websocket` v11 registration order gotcha.** Must be registered with `await fastify.register(fastifyWebsocket)` (or routes declared inside a nested `fastify.register(async (instance) => {...})` child context) BEFORE any `{websocket:true}` route is declared. Declaring the route synchronously right after an un-awaited `fastify.register(fastifyWebsocket)` on the same instance runs before the plugin's onRoute hook attaches — the handler then receives an object without `.send()`, causing a 500 on connect. See buglog bug-007. `backend/src/app.js` uses the nested-register pattern; keep it when touching that file.
- **[2026-08-01] Node 24's native global `WebSocket` client (undici-based) throws an internal `TypeError` in `#onSocketClose` against a `ws`-server (`@fastify/websocket`) in this container — root cause not isolated (likely an undici/Node 24 bug, not our code).** Use the `ws` npm package as the WS client in backend tests instead (`import { WebSocket } from 'ws'`), not the global. Confirmed reliable.
- **Backend test framework: Node's built-in `node:test` + `node:assert/strict`, zero extra deps for assertions.** Not pinned explicitly by the architecture spine, chosen to avoid adding an unpinned framework dependency. `ws` is the one exception (dev-only, for WS client tests - see above). Keep using `node:test` for all backend stories unless a real limitation forces a change.
- **This devcontainer's base image had no `make`/`gcc`/`python3`.** `better-sqlite3` (pinned in architecture) needs to compile from source via node-gyp when no prebuilt binary matches. Fixed by adding `build-essential` + `python3` to `.devcontainer/Dockerfile` (commit on `dev`, not story-specific) — also mirrored into `backend/Dockerfile` itself since `node:24-bookworm-slim` is equally minimal and the architecture spine already flagged this exact risk ("Docker base image... hrozí kompilace ze zdroje").
- **No `docker` binary in this devcontainer.** Cannot build-verify `backend/Dockerfile`/`docker-compose.yml`. Every story that touches Docker files should note this as an unverified-by-CI gap in its commit/TODO, not silently claim it works.
- **[2026-08-01] Firmware test strategy decision (no ESP32 hardware or toolchain available in this devcontainer).** Installed PlatformIO via `uv tool install platformio` (network access confirmed available). Firmware code is split: hardware-coupled files (ISR pulse counting, WiFi/HTTP, I2C sensor reads) live under `firmware/src/sense/`, `transmit/` (hardware parts), `config/`, `main.cpp` and depend on `Arduino.h` - genuinely untestable without real hardware, kept thin. Pure algorithmic logic (pulse-count→m/s, yaw correction→octant, buffer ring math, etc.) lives under `firmware/src/correct/` (and similar pure-only subpaths added as needed) with **zero** Arduino.h dependency, and IS unit-tested for real via PlatformIO's `[env:native]` (`platform = native`, host gcc, no ESP32 toolchain/hardware download - lightweight, ~5s). The `[env:esp32dev]` env is declared in every `platformio.ini` for documentation/real-hardware use but is NOT build-verified in this container (no toolchain fetched, no hardware to flash) - flagged per-story in TODO.md. `pio test -e native` is the actual CI-equivalent gate for firmware stories here.
- **PlatformIO native test env gotchas (see buglog bug-008) - required in every firmware `[env:native]` block:** `test_build_src = yes` (src/ isn't linked into test builds by default even with build_src_filter set) and `build_flags = -DUNITY_INCLUDE_DOUBLE` (Unity ships without double-precision assertions by default; TEST_ASSERT_EQUAL_DOUBLE silently fails without this flag).

## Key Learnings (session-process notes)

- **[2026-08-01] Real headless-browser smoke testing is available and worth using for dashboard stories.** `puppeteer-core` ships bundled with the globally-installed `openwolf` npm package (`/usr/lib/node_modules/openwolf/node_modules/puppeteer-core`) but has no browser binary of its own. `sudo apt-get install chromium` (~90MB, fast) provides one at `/usr/bin/chromium`; launch with `puppeteer.launch({executablePath: '/usr/bin/chromium', headless: true, args: ['--no-sandbox']})` (sandbox needs to be disabled running as root/in this container). Used in Story 3.2 to actually render the dashboard, confirm the Chart.js canvas has real pixel content (not blank/crashed), and check for console/page errors - caught nothing that session but is real coverage server-side `node:test` assertions structurally cannot provide (any DOM/Chart.js/browser-JS runtime error). Worth repeating for Story 3.3 and any future dashboard changes.
- **[2026-08-01] For every backend story, run a real smoke test (actual `node src/index.js` + curl) in addition to the injected/`:memory:` test suite before merging.** Story 1.6 caught a real bug (buglog bug-011: `openDb()` never created the DB file's parent directory) that all 22 passing `node:test` assertions missed, purely because every test uses `dbPath=':memory:'` and never touches the filesystem or starts a real listener. In-memory injected tests are fast and good for logic, but they cannot catch filesystem/startup/real-network issues - a quick manual boot + curl round-trip is cheap insurance every backend story should do before calling itself done, not just when something feels risky.
- **BMAD skill workflows assume a live interactive user at every menu ("halt and wait for [C] Continue").** When one of these skills is run inside an autonomous subagent invocation (Agent tool, no attached interactive user), there is no way to literally pause across turns — the skill's step files must be read and followed for *content/structure* discipline (extraction rigor, dependency rules, coverage validation), but the halt-for-approval menus have to be resolved using whatever brief/context the invoking session provided, standing in for the user's answers. Always flag this explicitly in the output (both in the artifact itself and in STATUS.md) so the real user knows no live back-and-forth happened and should spot-check the result once.
