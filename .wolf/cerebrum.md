## Key Learnings

- **Project:** gustik
- **[2026-08-01] `@fastify/websocket` v11 registration order gotcha.** Must be registered with `await fastify.register(fastifyWebsocket)` (or routes declared inside a nested `fastify.register(async (instance) => {...})` child context) BEFORE any `{websocket:true}` route is declared. Declaring the route synchronously right after an un-awaited `fastify.register(fastifyWebsocket)` on the same instance runs before the plugin's onRoute hook attaches — the handler then receives an object without `.send()`, causing a 500 on connect. See buglog bug-007. `backend/src/app.js` uses the nested-register pattern; keep it when touching that file.
- **[2026-08-01] Node 24's native global `WebSocket` client (undici-based) throws an internal `TypeError` in `#onSocketClose` against a `ws`-server (`@fastify/websocket`) in this container — root cause not isolated (likely an undici/Node 24 bug, not our code).** Use the `ws` npm package as the WS client in backend tests instead (`import { WebSocket } from 'ws'`), not the global. Confirmed reliable.
- **Backend test framework: Node's built-in `node:test` + `node:assert/strict`, zero extra deps for assertions.** Not pinned explicitly by the architecture spine, chosen to avoid adding an unpinned framework dependency. `ws` is the one exception (dev-only, for WS client tests - see above). Keep using `node:test` for all backend stories unless a real limitation forces a change.
- **This devcontainer's base image had no `make`/`gcc`/`python3`.** `better-sqlite3` (pinned in architecture) needs to compile from source via node-gyp when no prebuilt binary matches. Fixed by adding `build-essential` + `python3` to `.devcontainer/Dockerfile` (commit on `dev`, not story-specific) — also mirrored into `backend/Dockerfile` itself since `node:24-bookworm-slim` is equally minimal and the architecture spine already flagged this exact risk ("Docker base image... hrozí kompilace ze zdroje").
- **No `docker` binary in this devcontainer.** Cannot build-verify `backend/Dockerfile`/`docker-compose.yml`. Every story that touches Docker files should note this as an unverified-by-CI gap in its commit/TODO, not silently claim it works.
- **[2026-08-01] Firmware test strategy decision (no ESP32 hardware or toolchain available in this devcontainer).** Installed PlatformIO via `uv tool install platformio` (network access confirmed available). Firmware code is split: hardware-coupled files (ISR pulse counting, WiFi/HTTP, I2C sensor reads) live under `firmware/src/sense/`, `transmit/` (hardware parts), `config/`, `main.cpp` and depend on `Arduino.h` - genuinely untestable without real hardware, kept thin. Pure algorithmic logic (pulse-count→m/s, yaw correction→octant, buffer ring math, etc.) lives under `firmware/src/correct/` (and similar pure-only subpaths added as needed) with **zero** Arduino.h dependency, and IS unit-tested for real via PlatformIO's `[env:native]` (`platform = native`, host gcc, no ESP32 toolchain/hardware download - lightweight, ~5s). The `[env:esp32dev]` env is declared in every `platformio.ini` for documentation/real-hardware use but is NOT build-verified in this container (no toolchain fetched, no hardware to flash) - flagged per-story in TODO.md. `pio test -e native` is the actual CI-equivalent gate for firmware stories here.
- **PlatformIO native test env gotchas (see buglog bug-008) - required in every firmware `[env:native]` block:** `test_build_src = yes` (src/ isn't linked into test builds by default even with build_src_filter set) and `build_flags = -DUNITY_INCLUDE_DOUBLE` (Unity ships without double-precision assertions by default; TEST_ASSERT_EQUAL_DOUBLE silently fails without this flag).

- **[2026-08-09] `getHistory()` (backend/src/store/readings.js) compares `captured_at` as plain TEXT (`WHERE captured_at >= ?` against a generated ISO 'T'/'Z' cutoff string), and until bug-019 nothing validated that stored `captured_at` actually had that shape.** Any deviation (space instead of 'T', missing 'Z', missing/extra fraction digits) silently sorts wrong and drops the row from `/readings/history` forever — write still returns 201, no error anywhere. POST /readings now rejects non-canonical `capturedAt` with 400 (see ingest/routes.js `ISO_8601_UTC` regex). If you ever touch capturedAt handling again: real firmware always emits exactly `%Y-%m-%dT%H:%M:%S.000Z` (firmware/src/transmit/hw/clock.cpp) — validate against that exact shape, don't loosen it to "anything Date.parse accepts" or this class of bug returns.

- **[2026-08-09] Don't trust "it only fails in Docker" reports at face value before reproducing locally.** User reported the backend "doesn't work" via Docker (history table stuck at 00:00, new manual inserts invisible) and assumed it was Docker-specific. Root cause (bug-019: unvalidated `capturedAt` format breaking a string-comparison date filter) was fully reproducible with plain `node --test` against an in-memory DB and was already present in the local dev sqlite file from earlier local manual testing — it just hadn't been noticed locally. Always try to reproduce the reported symptom in the cheapest environment (no Docker needed here) before assuming the platform is the cause.

- [2026-08-01] `.wolf/hooks/post-write.js` exits early for EVERY path under `.wolf/` (self-referential-write guard) — it never pushes `.wolf/*` writes into `session.files_written`. Any Stop-hook check that inspects `files_written` to ask "was `.wolf/X` updated this session?" is structurally unsatisfiable (see bug-002, bug-004 in buglog.json — two independent instances of this exact pattern). If adding a new such check, check the target file's own `mtime` via `fs.statSync` against `session.started` instead (the pattern `checkStatusFreshness()` already uses correctly), never `files_written`.

- **[2026-08-01] Architecture spine finalized (Fast path + reviewer gate).** Backend: Node.js 24 + Fastify 5.11.x + better-sqlite3 (SQLite), not the addendum-mentioned FastAPI/Python — picked to reuse the devcontainer's already-set-up Node runtime rather than add a second language on a 16-day timeline. Firmware: C++/Arduino framework via PlatformIO. Dashboard: vanilla JS + Chart.js, no frontend build step, served as static assets by Fastify — one Docker image, one process. Full rationale + reviewer-gate findings: `_bmad-output/planning-artifacts/architecture/architecture-gustik-2026-08-01/.memlog.md`.
- **[2026-08-01, corrected 2026-08-01] ESP32 Arduino core version: 3.x, not the originally-decided "stable 2.x".** The architecture spine originally called for pinning "stable 2.x ESP32 core, not 3.x - PlatformIO support for 3.x is unsettled", but that call was made without ever actually running `pio run -e esp32dev` (assumed hardware-gated in this devcontainer; it's really only internet-gated for the toolchain download - first discovered true while setting up the CI pipeline, see buglog bug-017). The PlatformIO registry no longer serves any 2.x `framework-arduinoespressif32` release at all - only 3.x. `firmware/platformio.ini`'s `[env:esp32dev]` now leaves `framework = arduino` unpinned to a specific core version and lets `platform = espressif32 @ ~6.4.0` resolve its own default (currently 3.20011.230801) - confirmed to build clean (`pio run -e esp32dev`, SUCCESS). If this matters again: check the registry's currently-available versions before re-pinning anything, don't assume a decision recorded before a real build was ever attempted is still accurate.
- **[2026-08-01] ESP32 flash usage is tight: 90.6% (1.19MB/1.31MB) at the current code size**, confirmed by the real CI build (first one ever run - see above). No OTA mechanism exists (station is flashed by hand once, per Story 4.2's manual), so the default partition table's two-OTA-slot layout is wasted space here - a custom single-app partition table (`partitions.csv`, PlatformIO's `board_build.partitions` setting) would recover meaningful headroom (likely 300-500KB+) if flash usage becomes a real constraint later. Flagged in TODO.md, not implemented - out of scope for the CI pipeline task that surfaced it.
- **[2026-08-01] HMC5883L sourcing risk flagged.** Genuine HMC5883L magnetometer chips are discontinued; GY-271/273 modules sold today mostly ship QMC5883L die under HMC5883L silkscreen (different I2C address/registers). Architecture spine pins a dual-chip-compatible library (e.g. DFRobot_QMC5883) instead of a HMC5883L-only one — but the actual part Guru/Mlok source should be checked against this before ordering.
- **[2026-08-01] Epics/stories breakdown (`bmad-create-epics-and-stories`).** 5 epics, 18 stories, in `_bmad-output/planning-artifacts/epics.md`. Epic order follows PRD's literal priority ("funkční živé čtení > historický graf > vyladěná mechanika") as a strict sequence: Epic 1 walking-skeleton live path (FR-1,2,3,7,9,10,11) stands alone and fully functional even without Epic 2; Epic 2 layers connectivity resilience (buffer/backfill/LED/RSSI, FR-4,5,6) on top; Epic 3 historical graph (FR-8); Epic 4 zero-touch provisioning (FR-14,15); Epic 5 power/mechanical (FR-12,13, hardware-only, no software). ## Key Learnings (session-process notes)

- **[2026-08-01] `actionlint` (+ `shellcheck` for embedded run: scripts) catches real GitHub Actions mistakes that plain YAML parsing can't.** Not preinstalled; grab the binary via `curl -sL https://raw.githubusercontent.com/rhysd/actionlint/main/scripts/download-actionlint.bash | bash` (drops `./actionlint` in cwd) and `sudo apt-get install -y shellcheck` for the deeper check. Caught a real bug while writing `.github/workflows/ci.yml`: a job-level `if:` condition referencing `secrets.X` - the `secrets` context is not available in job-level `if:` at all (only `github`, `inputs`, `needs`, `vars` are), a mistake plain `yaml.safe_load()` can't catch since it's valid YAML/valid expression syntax, just semantically wrong for that context. Always run `actionlint` against new/changed workflow files before pushing - GitHub Actions failures are slow and annoying to iterate on compared to a local lint pass.
- **[2026-08-01] A "verified" architecture decision made before ever actually attempting the underlying build is not verified - go run it before trusting it, even under a plausible-sounding excuse ("hardware-gated") for why it wasn't tried.** The ESP32 Arduino core version pin (2.x, decided at architecture time) was accepted as final for the whole implementation phase on the assumption that building `[env:esp32dev]` needed physical hardware - it only needed internet access, which was available the entire time. Only surfaced as broken when the CI pipeline task actually ran `pio run -e esp32dev` for the first time (see buglog bug-017). Lesson: "this needs hardware to verify" is worth a second look before accepting it as a reason not to try - a devcontainer's tool availability isn't the same as a build's actual requirements.
- **[2026-08-01] Real headless-browser smoke testing is available and worth using for dashboard stories.** `puppeteer-core` ships bundled with the globally-installed `openwolf` npm package (`/usr/lib/node_modules/openwolf/node_modules/puppeteer-core`) but has no browser binary of its own. `sudo apt-get install chromium` (~90MB, fast) provides one at `/usr/bin/chromium`; launch with `puppeteer.launch({executablePath: '/usr/bin/chromium', headless: true, args: ['--no-sandbox']})` (sandbox needs to be disabled running as root/in this container). Used in Story 3.2 to actually render the dashboard, confirm the Chart.js canvas has real pixel content (not blank/crashed), and check for console/page errors - caught nothing that session but is real coverage server-side `node:test` assertions structurally cannot provide (any DOM/Chart.js/browser-JS runtime error). Worth repeating for Story 3.3 and any future dashboard changes.
- **[2026-08-01] For every backend story, run a real smoke test (actual `node src/index.js` + curl) in addition to the injected/`:memory:` test suite before merging.** Story 1.6 caught a real bug (buglog bug-011: `openDb()` never created the DB file's parent directory) that all 22 passing `node:test` assertions missed, purely because every test uses `dbPath=':memory:'` and never touches the filesystem or starts a real listener. In-memory injected tests are fast and good for logic, but they cannot catch filesystem/startup/real-network issues - a quick manual boot + curl round-trip is cheap insurance every backend story should do before calling itself done, not just when something feels risky.
- **BMAD skill workflows assume a live interactive user at every menu ("halt and wait for [C] Continue").** When one of these skills is run inside an autonomous subagent invocation (Agent tool, no attached interactive user), there is no way to literally pause across turns — the skill's step files must be read and followed for *content/structure* discipline (extraction rigor, dependency rules, coverage validation), but the halt-for-approval menus have to be resolved using whatever brief/context the invoking session provided, standing in for the user's answers. Always flag this explicitly in the output (both in the artifact itself and in STATUS.md) so the real user knows no live back-and-forth happened and should spot-check the result once.
