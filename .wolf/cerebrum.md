## Key Learnings

- **Project:** gustik
- **[2026-08-15] Standalone hardware bring-up sketches live in `firmware/src/diag/`, one PlatformIO env each, and MUST be excluded from `[env:esp32dev]`.** Each has its own `setup()`/`loop()`, so linking one alongside `main.cpp` is a duplicate-symbol error. The pattern: `[env:esp32dev]` carries `build_src_filter = +<*> -<diag/>`, and each diag env carries `build_src_filter = -<*> +<diag/<name>.cpp>`. First instance: `diag/vane_diag.cpp` / `[env:vane_diag]`. CI build-verifies every diag env alongside `esp32dev` (same cached toolchain, ~3s each) so they can't rot against changed pin constants. A diag sketch deliberately depends on *nothing* else in `src/` — no WiFi, no config.txt, no other sensors — so a failure it reports is unambiguously about the one peripheral under test.
- **[2026-08-15] A sensor bring-up diagnostic must decode against the *datasheet*, never against the firmware's own calibration table.** `sense/vane.cpp`'s `kOctantAdcReadings` is exactly the thing under suspicion (placeholder, never measured), so `diag/vane_diag.cpp` derives its expected levels at runtime from Fine Offset's published resistances + the pull-up/supply constants (`mV = supply * R/(R+pullUp)`) and reports the *margin to the runner-up match* alongside the error — a small margin means two positions are physically indistinguishable at this pull-up value, which is a wiring verdict the raw error alone can't give. It then emits a paste-ready `kOctantAdcReadings[8]`, closing the loop from measurement to calibration. Two ESP32-specific points baked in: use `analogReadMilliVolts()` (eFuse-calibrated) for the decode and raw `analogRead()` only for the paste-ready table, since that's what vane.cpp compares; and 11dB attenuation saturates around ~3.1V, so the 120kΩ (270°) and 64.9kΩ (315°) positions sit near the ceiling — if they collapse into one level the fix is a smaller pull-up (4.7kΩ), not a calibration tweak.
- **[2026-08-01] `@fastify/websocket` v11 registration order gotcha.** Must be registered with `await fastify.register(fastifyWebsocket)` (or routes declared inside a nested `fastify.register(async (instance) => {...})` child context) BEFORE any `{websocket:true}` route is declared. Declaring the route synchronously right after an un-awaited `fastify.register(fastifyWebsocket)` on the same instance runs before the plugin's onRoute hook attaches — the handler then receives an object without `.send()`, causing a 500 on connect. See buglog bug-007. `backend/src/app.js` uses the nested-register pattern; keep it when touching that file.
- **[2026-08-01] Node 24's native global `WebSocket` client (undici-based) throws an internal `TypeError` in `#onSocketClose` against a `ws`-server (`@fastify/websocket`) in this container — root cause not isolated (likely an undici/Node 24 bug, not our code).** Use the `ws` npm package as the WS client in backend tests instead (`import { WebSocket } from 'ws'`), not the global. Confirmed reliable.

- **[2026-08-09] Don't trust "it only fails in Docker" reports at face value before reproducing locally.** User reported the backend "doesn't work" via Docker (history table stuck at 00:00, new manual inserts invisible) and assumed it was Docker-specific. Root cause (bug-019: unvalidated `capturedAt` format breaking a string-comparison date filter) was fully reproducible with plain `node --test` against an in-memory DB and was already present in the local dev sqlite file from earlier local manual testing — it just hadn't been noticed locally. Always try to reproduce the reported symptom in the cheapest environment (no Docker needed here) before assuming the platform is the cause.

- **[2026-08-10] `docker image prune -f` with no filter is daemon-wide, not project-scoped — never run it unfiltered on a shared host.** While manually dry-running the new `deploy-backend` CI step over SSH on `bombur.remesh.cz` (a shared host running several other people's Docker projects — grafana, prometheus, teamspeak, caddy, mariadb), the original (pre-existing, inherited from an earlier session) `docker image prune -f` reclaimed 1.5GB of *other* projects' dangling images — outside the "don't touch anything outside the deployment directory" boundary I'd been given for this task, even though no running container was affected (prune only removes images with zero container references). Fixed by scoping to this project's own label: `docker image prune -f --filter 'label=com.docker.compose.project=gustik'` (confirmed the compose-built image actually carries that label via `docker image inspect`). Always scope prune commands on any host you don't fully own, even one command that "should" only affect dangling/unused resources.
- [2026-08-01] `.wolf/hooks/post-write.js` exits early for EVERY path under `.wolf/` (self-referential-write guard) — it never pushes `.wolf/*` writes into `session.files_written`. Any Stop-hook check that inspects `files_written` to ask "was `.wolf/X` updated this session?" is structurally unsatisfiable (see bug-002, bug-004 in buglog.json — two independent instances of this exact pattern). If adding a new such check, check the target file's own `mtime` via `fs.statSync` against `session.started` instead (the pattern `checkStatusFreshness()` already uses correctly), never `files_written`.

- **[2026-08-11] Never trust an architecture-time chip assumption over bench-verified evidence sitting elsewhere in the repo.** `sense/magnetometer.cpp` had implemented against QMC5883L (address `0x0D`) since 2026-08-01, flagged in TODO.md/STATUS.md as "should be confirmed" but never actually checked against `scripts/` (added later, `d901ee9`) - a bench Python driver that had *already* established the real chip is QMC5883P (`0x2C`, different register map) via a USB-I2C bridge. Lesson: when a hardware-identity question has an open TODO flag, actively search the repo for anything that might have already answered it (a `scripts/`, `hardware/`, `docs/` folder someone else populated) before trusting the original placeholder assumption - see bug-029.
- **[2026-08-12] For hardware wiring questions (connector pinouts, resistor values, power requirements), fetch the actual manufacturer datasheet rather than answering from memory - and PDFs that WebFetch's text-summarizer can't parse can often still be read directly with the Read tool once downloaded (it renders PDF tables/diagrams that a text-extraction summary misses).** For the WH1080/WH1090 wind sensor RJ11 pinout, WebFetch on a Sparkfun/community page gave partial, sometimes-conflicting answers; fetching Shenzhen Fine Offset Electronics's own datasheet PDF (the actual manufacturer) and reading it directly with the Read tool (after WebFetch's summarizer failed on it) gave a complete, authoritative pinout + resistance table + explicit "no active electronics" power statement in one source. See `docs/hardware/wind-sensor-wiring.md`. Worth repeating for any other salvaged-sensor wiring question this project hits (rain gauge from the same station is a likely future one, same datasheet already covers it).
- **[2026-08-12] A "successful" HTTP response from firmware does not mean the backend actually stored anything - always check the idempotency/dedup logic on both ends before trusting `sent=yes`.** bug-031: `POST /readings` (`backend/src/ingest/routes.js`) returns 201 unconditionally, even when `insertReading()`'s `ON CONFLICT(client_id) DO NOTHING` silently no-ops a duplicate `client_id` (the readings table has `client_id TEXT NOT NULL UNIQUE`, a deliberate Story 2.2 backfill-retry safety net). Firmware's `makeClientId()` combined a persistent `WiFi.macAddress()` with a RAM counter that resets to 0 every boot - so any reboot (routine during real-hardware bring-up/testing) regenerated clientIds a previous boot already sent and stored, and every post-reboot POST silently vanished while Serial kept reporting `sent=yes`. This is a real trap for any device/backend pair with idempotent-insert dedup: the write-side "success" status code and the read-side "did it actually persist" question are different things, and a design that conflates them (routes.js not checking `inserted` before returning 201) will hide exactly this class of bug. If touching the ingest route again, consider surfacing `inserted` count separately from `written` count in the response - would have made this bug visible from the HTTP response alone instead of needing a live device+backend cross-check to diagnose.
- **[2026-08-12] This devcontainer now has direct access to the real ESP32 hardware (`/dev/ttyUSB0`, user already in `dialout`) AND outbound internet to the real deployed backend (`https://gustik.remesh.cz`) - both were previously assumed only available on Mlok's own machine (see 2026-08-11 notes below).** Confirmed by directly flashing new firmware (`~/.platformio/penv/bin/pio run -t upload -e esp32dev`) and curling the live backend to verify a real fix end-to-end in one session, without needing Mlok to run anything by hand. Re-check this assumption before ever again writing "no ESP32 hardware in this devcontainer" as a blocker - it may no longer be true. Capturing serial output non-interactively: opening the port (even just via `stty`) can produce a burst of garbled/duplicated-looking bytes for the first moment (looked like a rapid "=0" flood in one capture) that is a capture/settling artifact, not a device bug - re-capture a fresh short window after the port has been open a few seconds before trusting what you see.
- **[2026-08-12] Any blocking hardware call in firmware/src/*/hw/ needs an explicit bounded timeout, checked from day one, not just WiFi/HTTP/NTP.** bug-030: the magnetometer's I2C reads (Wire.beginTransmission/endTransmission/requestFrom in sense/magnetometer.cpp) had no timeout and no return-code checking, unlike every other blocking call in this codebase (WiFi connect 5000ms, NTP sync 5000ms, HTTPClient's own default). The first time the magnetometer was physically wired to real hardware, an I2C hang froze the whole `loop()` silently - no Serial output (the one per-cycle print came after the hang), no more sends, no crash. arduino-esp32's I2C driver is documented to lock up on a stuck bus/clock stretching/unresponsive device (upstream issues #349, #5934) - `Wire.setTimeOut(1000)` bounds it (1000ms is the smallest some 3.x releases actually honor). Lesson: when adding a new hardware-coupled peripheral, audit every blocking driver call for a timeout before it's ever tested against real silicon, don't wait for a live freeze to discover the one that's missing one.
- **[2026-08-12] `WifiTransmitClient::ensureWifiConnected()`'s original reconnect logic picked a network by scan-visibility only (`selectNetworkIndex`), so a configured network that's visible but unconnectable (wrong password, AP rejecting the station) would be retried forever every cycle, never falling through to the other configured network even though it was also in range.** Fixed by looping `selectNetworkIndex` + a bounded connect attempt across all configured networks in priority order within one `ensureWifiConnected()` call, removing an SSID from the candidate pool after a failed connect attempt so the next iteration picks the next-priority one. Keep this in mind for any future change to the reconnect path - visibility (is the SSID in the scan) and connectability (does the handshake succeed) are different conditions and both must be checked.
- **[2026-08-11] Mount-orientation sign flips belong in the hardware read layer, not the pure/tested correction math.** The real magnetometer mount was bench-confirmed as `up=-z, forward=+x` (chip mounted upside down), which requires negating the raw Y axis before it reaches `atan2`. Put that negation in `sense/magnetometer.cpp`'s `readRawXY()` (hardware-coupled, untested by construction) rather than changing `correct/wind_direction.cpp`'s `atan2(y, x)` (pure, unit-tested, and meant to stay mount-agnostic) - keeps the existing architecture split (pure algorithm vs. hardware quirk) intact. The calibration constant in `main.cpp` that gets subtracted afterward must be expressed in the same (already-flipped) coordinate frame the hardware layer returns - documented inline in both files since this indirection is easy to get backwards on a future edit.

- **[2026-08-10] Backend deploy moved to a GHCR registry-push flow, GHCR image kept private with a fresh ephemeral login every deploy.** Was: CI verifies the Dockerfile builds, then rebuilds it again from source on the server (`docker compose up -d --build`) - two separate builds of the same commit, no guarantee they produce identical bytes. ## Key Learnings (session-process notes)

- **[2026-08-01] `actionlint` (+ `shellcheck` for embedded run: scripts) catches real GitHub Actions mistakes that plain YAML parsing can't.** Not preinstalled; grab the binary via `curl -sL https://raw.githubusercontent.com/rhysd/actionlint/main/scripts/download-actionlint.bash | bash` (drops `./actionlint` in cwd) and `sudo apt-get install -y shellcheck` for the deeper check. Caught a real bug while writing `.github/workflows/ci.yml`: a job-level `if:` condition referencing `secrets.X` - the `secrets` context is not available in job-level `if:` at all (only `github`, `inputs`, `needs`, `vars` are), a mistake plain `yaml.safe_load()` can't catch since it's valid YAML/valid expression syntax, just semantically wrong for that context. Always run `actionlint` against new/changed workflow files before pushing - GitHub Actions failures are slow and annoying to iterate on compared to a local lint pass.
- **[2026-08-01] A "verified" architecture decision made before ever actually attempting the underlying build is not verified - go run it before trusting it, even under a plausible-sounding excuse ("hardware-gated") for why it wasn't tried.** The ESP32 Arduino core version pin (2.x, decided at architecture time) was accepted as final for the whole implementation phase on the assumption that building `[env:esp32dev]` needed physical hardware - it only needed internet access, which was available the entire time. Only surfaced as broken when the CI pipeline task actually ran `pio run -e esp32dev` for the first time (see buglog bug-017). Lesson: "this needs hardware to verify" is worth a second look before accepting it as a reason not to try - a devcontainer's tool availability isn't the same as a build's actual requirements.
- **[2026-08-01] Real headless-browser smoke testing is available and worth using for dashboard stories.** `puppeteer-core` ships bundled with the globally-installed `openwolf` npm package (`/usr/lib/node_modules/openwolf/node_modules/puppeteer-core`) but has no browser binary of its own. `sudo apt-get install chromium` (~90MB, fast) provides one at `/usr/bin/chromium`; launch with `puppeteer.launch({executablePath: '/usr/bin/chromium', headless: true, args: ['--no-sandbox']})` (sandbox needs to be disabled running as root/in this container).
