Recommendation: `no_std` + `esp-hal` 1.1.2 + `esp-radio` + `esp-rtos` + Embassy, in a **parallel `firmware-rs/` Cargo workspace** — `firmware/` stays the deployed artifact and is not touched (the regatta target is mid-August 2026, i.e. now). Two sharp edges found: the ESP32-WROOM is Xtensa so `espup`'s compiler fork is still mandatory (upstream rustc lists the targets Tier 3 but ships no Xtensa LLVM backend), and `no_std` TLS with real certificate verification needs the git-only `esp-mbedtls` (`embedded-tls` on crates.io does **not** verify certs in `no_std`, which is unacceptable for a device carrying the ingest bearer token onto borrowed Wi-Fi). Plan puts all pure logic in a route-agnostic `gustik-core` crate so a pivot to the `std` route would rewrite only `main.rs`. **Mlok answered Q1–Q4 the same day and all six docs were re-spun to match**: chip stays ESP32-WROOM (RISC-V considered but none at hand); `no_std` confirmed; **certificate verification explicitly not required** ("security is not really important here… encryption still prevents sniffing the bearer token; I don't assume a malicious actor with an AP") — an informed risk acceptance, recorded as such, which removed the git deps and mbedTLS entirely; and the `qmc5883p` crate is used instead of a hand-written driver, so the planned `gustik-drivers` crate was dropped. Two claims were then verified against reality rather than assumed: the live backend completes a TLS 1.3 handshake restricted to exactly what `embedded-tls` implements (`curl --tls13-ciphers TLS_AES_128_GCM_SHA256 --curves X25519 …/health` → 200) and serves an ECDSA rather than RSA cert; and the `qmc5883p` crate's register map matches ours on every point except the undocumented `0x0D = 0x40` write, which our own bench notes say the sensor works without. **Nothing is blocking a start now** — Q5–Q8 (second bench board, `defmt` vs plain text, repo placement, whether it ever ships) remain open but gate nothing. Phase 1 (port `gustik-core` + its 57 tests, host-only `cargo test`) needs no `espup` and no hardware.

## 📁 Active architecture

- **Stack:** Backend: Node.js 24 + Fastify 5.11.x + better-sqlite3 13.0.x + `@fastify/websocket` + `@fastify/static@10.1.2` (pinned above 8.x/9.x — high-severity path-traversal/auth-bypass advisory), tested with built-in `node:test`. Firmware: C++/Arduino (ESP32 core 2.x) via PlatformIO, pure logic tested via `pio test -e native` (Unity, needs `test_build_src=yes` + `-DUNITY_INCLUDE_DOUBLE`). Dashboard: vanilla JS, Chart.js 4.5.1 vendored (no CDN, no build step).
- **Key tables / modules:** SQLite `readings` table (pinned schema) in `backend/src/store/` (snake_case↔camelCase boundary lives only here). `backend/src/ingest` (write + backfilled-flag decision), `backend/src/serve` (read + WS + history-changed broadcast + history endpoint), `backend/src/health`, `backend/src/static` (dashboard: `index.html`/`dashboard.js`/`live-socket.js`/`history-chart.js`/`history-chart-data.js`/`format.js`/`manual.html`/`vendor/chart.umd.min.js`). `firmware/src/sense` (hardware I/O, untested), `firmware/src/correct` (pure logic, tested), `firmware/src/transmit` (payload/connection-monitor/led-policy/rssi-latch/ring-buffer/buffer-capacity pure logic tested; `transmit/hw/` WiFi+HTTP+clock+flash hardware, untested), `firmware/src/config` (station_config parser + network selector, tested; `config/hw/` LittleFS loader, untested), `firmware/data/config.example.txt` (WiFi/token template, real `config.txt` gitignored), `firmware/src/main.cpp` (wiring).
- **Patterns:** One PlatformIO test directory per test case (`test/test_<name>/test_<name>.cpp`, own `main()`). Firmware pure logic (no Arduino.h) vs hardware-coupled code kept in separate files/dirs. One shared WS connection on the dashboard (`live-socket.js`) instead of per-feature sockets. Backend: every story gets a real smoke test (curl) in addition to injected `:memory:` tests, and dashboard stories get a real headless-Chromium render check.
